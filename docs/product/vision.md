# 产品愿景与范围

## 产品目标

帮助车主在一个连续的线上流程中提交续保材料、核对车辆与车主信息、查看报价并办理核保；办理过程之外，用户也可以快速咨询保险知识。

## 首期用户体验

- 用户可以上传材料或手动补充信息，查看识别结果并确认资料。
- 核保前必须具备以下五项车主资料：VIN 码、发动机号、身份证号、车主姓名、车牌号。任一项缺失、未确认或存在未解决冲突时，系统不得发起核保请求。
- 续保进度和已确认资料在刷新或短暂断线后仍能恢复。
- 保险知识问答应快速返回有依据的答复，并与正在等待核保的任务互不阻塞。

以上是产品方向。可测试的具体行为、错误情形和验收标准由 OpenSpec 的主 spec 与活动 change 定义。

## 产品边界

- 保险公司返回的报价、核保和出单状态是业务结果的依据；模型只能解释或编排，不能替保险公司作出承保决定。
- 前端提示不能取代服务端核保门禁。
- 问答属于独立知识服务，不持有修改续保案件、报价、核保或出单的工具。
- 初期以车险续保为中心，不扩展到全品类保险销售、理赔处理或通用保险经纪平台。

## 设计原则

1. **资料先核实，业务后提交。** 上传识别出的内容需要经过确认；缺少必填资料时阻断后续业务写操作。
2. **业务状态可追溯。** 续保案件状态由业务服务持久化；Agent 文本和浏览器页面不作为业务记录。
3. **办理与咨询相互隔离。** 知识问答按有界的检索和回答流程处理，不等待或占用续保流程。
4. **每一步能解释。** 用户看到资料缺项、待确认项和核保进展时，可以知道下一步需要做什么。

## 需求入口

字段校验、资料冲突、会话恢复、知识问答和核保门禁的验收规则维护在 [`openspec/specs/`](../../openspec/specs/) 与 [`openspec/changes/`](../../openspec/changes/) 中。功能范围或用户可观察行为改变时，先修改相应 OpenSpec change。
