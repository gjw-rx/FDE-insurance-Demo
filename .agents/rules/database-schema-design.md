# database-schema-design

## 1. 适用范围与优先级

- 本规则适用于业务 API 的全部 MySQL 表结构、索引、迁移和受控取值设计，包括 `apps/api/drizzle/` 下的 schema 与迁移文件。
- 根目录 [`AGENTS.md`](../../AGENTS.md)、OpenSpec change 和已确认的主 spec 优先于本规则；本规则只约束表结构如何设计与交付，不改变产品需求或接口契约。
- 当前技术栈为 MySQL 8.0 与 `mysql2` + Drizzle（版本以 `apps/api/package.json` 和根 `pnpm-lock.yaml` 为准），实现位置见 `docs/tech/mysql.md`，不自行升级或替换数据库与迁移工具。
- 具体表的字段与注释以已批准的活动 change `design.md` 为准；本规则给出通用约束，两者冲突时先确认再实施，不以规则覆盖已批准设计。

## 2. DDL 评审门禁（最高优先级）

- 任何 CREATE TABLE、ALTER TABLE、索引调整或取值约束变更，都 SHALL 先以候选 DDL 形式提交人工 review；评审稿写在对应 change 的 `design.md` 中，包含完整建表语句、字段中文注释、约束与索引清单。
- 在获得明确批准前，SHALL NOT 创建业务表 schema 定义、生成迁移文件、执行 DDL 或对任何数据库做结构变更。
- 批准结论 SHALL 记录在 change 内，包含批准日期、最终字段清单和所有修改项；后续任何字段调整都必须重新走同一门禁。
- 迁移文件一旦被应用即为历史，禁止回改已执行的迁移；结构变化以新增迁移追加实现。
- API 进程 SHALL NOT 在启动时隐式执行迁移；迁移由发布阶段显式执行，失败以非零状态终止且不记录为已完成。

## 3. 命名规范

- 表名、字段名、索引名、约束名统一使用小写 `snake_case`，禁止驼峰、大小写混用和中文拼音缩写。
- 表名使用单数业务名词，例如 `chat_session`、`chat_message`，不使用复数或 `tbl_` 前缀。
- 字段命名规则：
  - 主键使用 `<实体>_id`（如 `session_id`、`run_id`），不使用裸 `id`。
  - 时间字段以 `_at` 结尾（`created_at`、`updated_at`、`finished_at`）。
  - 布尔语义字段以 `is_` / `has_` 开头，并使用 `TINYINT(1)` 或 `BOOLEAN`。
  - 排序/序号字段使用 `*_order`，明确表达“顺序位”而非“数量”。
  - 状态、类型、来源等受控取值字段使用 `status`、`role`、`*_source` 等语义名，不使用 `type1`、`flag`。
- 索引与约束命名：
  - 主键由 InnoDB 隐式命名，不额外声明名字。
  - 唯一索引使用 `uq_<表名>_<字段...>`，普通索引使用 `idx_<表名>_<字段...>`。
  - 不使用 MySQL 自动生成的索引名，避免不同环境名字不一致导致迁移漂移。

## 4. 结构规模约束

- 每张表字段数 SHALL 少于 30 个（含主键），超出说明需要拆分实体，而不是继续加列。
- 每张表索引数 SHALL 少于 5 个（含主键与唯一索引）。索引数量达到上限时优先复核查询模式，而不是删索引凑数。
- 每张表 SHALL 禁止使用外键（`FOREIGN KEY`）与级联（`ON DELETE` / `ON UPDATE`）：
  - 关联完整性由仓储事务、唯一约束和启动校验共同保证，不能依赖数据库级联。
  - 无外键不表示可以出现孤立记录；写入必须在同一事务内完成关联写入，并具备可重复的完整性检查。
- 存储引擎固定 `InnoDB`，字符集固定 `utf8mb4`，排序规则固定 `utf8mb4_0900_ai_ci`，避免不同环境默认值差异。
- 主键使用应用层生成的 `CHAR(36)` UUID，不使用自增主键暴露记录规模；`run_id`、`session_id` 等业务标识同样由应用层生成。
- 时间字段使用 `DATETIME(3)` 并由应用层写入，不使用数据库服务器时钟（`CURRENT_TIMESTAMP` 默认值）、不使用 `TIMESTAMP`，避免时区与测试不确定性。

## 5. 字段注释与可读性

- 每个字段和每张表 SHALL 带中文 `COMMENT`，说明业务语义、取值来源或非显然的约束原因，而不是复述类型。
- 注释 SHALL NOT 包含身份证号、材料正文、凭据、内部地址或其它敏感数据；正文类字段的注释只说明敏感性与使用限制。
- 当前 `drizzle-orm@0.45.2` 的 `mysql-core` 不支持列注释 API，因此注释只能落在迁移 SQL 内：
  - 由 `drizzle-kit` 生成迁移后在同一个迁移文件中补齐 `COMMENT`，不另建注释副本；
  - 后续迁移若 `MODIFY` 到带注释的列，必须连同原注释一起重写，否则注释会被清除；
  - 已应用结构的注释通过 `information_schema.columns` / `information_schema.tables` 校验，证明注释真实落库。

## 6. 受控取值使用逻辑枚举

- SHALL NOT 使用 MySQL `ENUM` 类型，也 SHALL NOT 使用 TypeScript `enum` 关键字或枚举类；状态、角色、来源、原因等受控取值统一采用逻辑枚举：数据库中存字符串取值的 `VARCHAR` 列，代码中使用字符串字面量联合类型。
- 取值合法性 SHALL 由应用层负责：写入前校验取值，非法取值必须在产生数据库副作用之前被拒绝。数据库层不加 `CHECK` 取值约束，也不为取值建立字典表（字典表需要外键或额外查询，与第 4 条冲突）。
- 取值的运行时定义 SHALL 只有一处来源，即在 `packages/contracts` 维护取值数组，并由该数组派生联合类型；SHALL NOT 在迁移 SQL、仓储、前端、测试或文档副本中重复写死取值清单。
- `VARCHAR` 长度按契约中最大取值与合理扩展预留，取值新增或调整只改契约，不改库结构。
- 读取到契约外的未知取值（人工写入、旧版本遗留）时 SHALL 返回稳定错误并保留脱敏诊断，不得把未知取值透传给对外契约。

## 7. 无外键下的完整性与并发

- 关联写入 SHALL 在同一事务内完成；需要“先占位再补全”的场景必须能通过唯一约束识别重复，而不是依赖先查后写。
- 可能重复提交的写操作 SHALL 由业务唯一键保证幂等（例如 `(run_id, role)`），重复请求返回既有记录且不重复产生副作用。
- 需要严格顺序的场景（如会话内消息顺序）使用行锁在事务内分配序号，并保证分配的序号单调递增；SHALL NOT 依赖时间戳或随机 ID 推断顺序。
- 状态字段 SHALL 有明确终态语义；更新终态的操作必须幂等，较早操作晚返回时不得覆盖较新的状态。
- 进程重启后 SHALL 能识别并收敛遗留的非终态记录，恢复过程本身幂等，且不重复触发外部副作用。
- 允许的有限重试只针对明确可重试的错误（如死锁）并设有次数上限；SHALL NOT 使用无上限重试掩盖结构性失败。

## 8. 验证方式

- 结构约束使用静态检查与人工清单验证：无 `FOREIGN KEY`、无 `ENUM`、无 `CHECK` 取值清单、字段为 `snake_case`、每表字段数与索引数满足上限。
- 注释与结构使用真实查询验证，例如查 `information_schema.columns`、`information_schema.tables` 与 `information_schema.statistics`，证明字段、注释、索引和唯一约束与批准版一致。
- 迁移使用隔离的非生产 MySQL 执行首次、重复、并发和失败路径验证；失败必须非零退出且不记录为已完成。测试不得连接生产库，不得在 fixture、日志或证据中保存真实凭据。
- 事务、幂等与恢复行为必须有真实 MySQL 集成测试；SHALL NOT 用内存替身或 mock DAO 证明 SQL 边界、参数化查询或事务正确性。
- 验证结果记录真实命令、退出码和证据路径；未执行项保持“未执行”，不得写成通过。

## 9. 例外与变更

- 确需突破第 4、6 条限制时（例如确需外键、`ENUM` 或超过索引上限），必须先建立独立 change，说明替代方案、影响与验证方式，经评审确认后再实施。
- 表结构约束的调整同步更新本规则、`docs/tech/mysql.md` 与相关 change 的 `design.md`；只改其中一处视为未完成。
